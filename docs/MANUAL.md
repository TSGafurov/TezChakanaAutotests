# Мануал: как работать с этим проектом без Claude

Этот файл написан на случай, если рядом не будет ассистента — здесь есть всё, что
нужно, чтобы запускать существующие автотесты, писать новые и менять старые. Читай по
порядку, если начинаешь с нуля; если что-то одно нужно — переходи сразу к разделу.

Смежные документы:
- [`README.md`](../README.md) — краткая версия того же самого, держи в актуальном состоянии вместе с этим файлом.
- [`docs/exploration-notes.md`](exploration-notes.md) — живая матрица покрытия (какие сценарии приложения покрыты тестами, какие нет) + подробный журнал всех найденных багов приложения и инфраструктуры (SYS-01..SYS-17 и т.д.). Загляни туда, прежде чем добавлять новый тест — возможно, сценарий уже описан или уже известно, почему он не автоматизирован.

## 0. Что это вообще такое

Appium + TestNG UI-автотесты для Android-приложения "Tez Chakana"
(`uz.agrobank.chakanaexpress`, Flutter-приложение). Тесты гоняются против
**реального личного аккаунта владельца на живом продовом бэкенде** — не изолированный
QA-стенд. На нём реальные заказы, адреса, карты. Это накладывает два важных
ограничения на весь проект:

1. **Осторожность прежде всего.** Не подключай `OrderErrorTest`/`OrderRetryTest` в сьют
   и не меняй `phone.number`/`otp.code` без явного согласия владельца — эти тесты могут
   создать реальный заказ или дёрнуть реальный SMS. Подробности — в README и
   `docs/exploration-notes.md` (раздел про инциденты — там были случаи, когда баг в
   автотестах реально создавал заказы/дублировал адреса).
2. **Состояние аккаунта "плывёт" между прогонами.** Сессии используют `NoReset(true)` —
   это значит, что данные приложения (логин, корзина, язык интерфейса) сохраняются
   между отдельными Appium-сессиями. Тест, который меняет состояние (например,
   разлогинивает аккаунт или кладёт товар в корзину) и не убирает за собой, ломает
   *следующий* тест в сьюте, а не только себя. Это была причина большинства
   найденных в этом проекте системных багов (SYS-13, SYS-16 в exploration-notes.md) —
   имей это в виду, когда пишешь новый тест или меняешь навигацию.

**На 2026-09-16 важно:** статический тестовый OTP-код (`081020`), на который были
завязаны все тесты логина, **отключён бэкендом** — вход в тестах сейчас не работает
(см. `feedback_login_otp` в памяти проекта и SYS-17 в exploration-notes.md). Пока
разработка не даст новый код, тесты с реальным логином (`CheckoutFlowTest`,
`ProfileGuestTest` и т.п.) будут либо падать на вводе OTP, либо просто идти в
гостевом состоянии — это ожидаемо, не пытайся это чинить как баг тестов.

## 1. Окружение с нуля

Если на машине ничего не настроено:

```bash
# Java 21 и Maven
brew install openjdk@21 maven

# Android SDK + эмулятор (если ставишь через Android Studio - можно пропустить,
# студия сама ставит platform-tools/emulator)
brew install --cask android-commandlinetools

# Appium (CLI-сервер, версия 3.x)
npm install -g appium
appium driver install uiautomator2
```

Тебе также нужен уже настроенный Android-эмулятор (AVD) с установленным APK
`uz.agrobank.chakanaexpress` и залогиненным (или гостевым — зависит от того, что
тестируешь) реальным аккаунтом владельца. Этот проект не устанавливает APK сам —
устройство/эмулятор должно быть готово заранее (`adb devices` должен его видеть).

### Запуск эмулятора и Appium перед каждой сессией тестирования

```bash
# 1. Эмулятор (имя AVD в этом проекте - Medium_Phone, посмотри своё через `emulator -list-avds`)
emulator -avd Medium_Phone -netdelay none -netspeed full &

# дождаться полной загрузки:
adb wait-for-device
until [ "$(adb shell getprop sys.boot_completed 2>/dev/null | tr -d '\r')" = "1" ]; do sleep 2; done

# 2. Appium-сервер (по умолчанию слушает 127.0.0.1:4723)
appium &

# 3. Убедиться, что оба видны
adb devices
curl -s http://127.0.0.1:4723/status
```

Если приложение не запущено на эмуляторе после его загрузки — тесты сами не
запускают его с нуля (`NoReset(true)`, приложение должно уже существовать со своими
данными). При необходимости подними его вручную:

```bash
adb shell am start -n uz.agrobank.chakanaexpress/.MainActivity
```

### Перезапуск эмулятора, если что-то "тупит"

Долгий аптайм эмулятора (несколько часов) реально деградирует его — тесты начинают
падать по таймауту на совершенно разных, не связанных друг с другом экранах (см.
"Emulator resource exhaustion" в памяти проекта / Known issue в exploration-notes.md).
Если это происходит — не чини код, просто перезапусти эмулятор:

```bash
adb -s emulator-5554 emu kill      # НЕ kill -15 на pid - именно эта команда,
                                    # она даёт эмулятору корректно сохраниться и выйти
sleep 10
emulator -avd Medium_Phone -netdelay none -netspeed full &
```

## 2. Настройка (`config.properties`)

Все тестовые данные (номер телефона, OTP, названия магазинов/категорий/товаров,
адреса) читаются из `src/test/resources/config.properties` — этот файл **не в git**
(содержит реальный номер и OTP). Перед первым запуском:

```bash
cp src/test/resources/config.properties.example src/test/resources/config.properties
# открой файл и подставь реальные значения (номер телефона владельца, актуальный OTP)
```

Любое значение можно переопределить флагом при запуске, не трогая файл:

```bash
mvn test -Dphone.number=... -Dotp.code=...
```

Смотри `TestConfig.java` — там весь список доступных ключей как типизированные
методы (`TestConfig.phoneNumber()`, `TestConfig.storeName()` и т.д.). Если добавляешь
новый тест, которому нужно новое тестовое значение (например, название новой
категории) — добавь ключ и в `config.properties.example`, и в `config.properties`, и
геттер в `TestConfig.java`, а не хардкодь строку прямо в тесте (см. раздел 5 про POM).

## 3. Как запустить тесты

### 3.1. Только безопасное подмножество (рекомендуется по умолчанию)

Ничего не меняет в реальном аккаунте — read-only проверки. Годится гонять часто,
даже автоматически:

```bash
mvn test -DsuiteXmlFile=src/test/resources/testng-safe.xml
```

### 3.2. Полный регресс (safe + mutating)

Меняет реальные данные (корзину, адреса, язык интерфейса, уведомления), но **не**
создаёт реальных заказов (см. раздел про уровни риска ниже). Гонять осознанно, не
"на автомате":

```bash
mvn test -DsuiteXmlFile=src/test/resources/testng.xml
# (то же самое, что просто `mvn test`, т.к. testng.xml - дефолт в pom.xml)
```

⚠️ На практике полный прогон (14 классов, ~40+ минут) на среднем ноутбуке часто **не
укладывается в доступную память хоста** и получает OOM-килл от ОС, если параллельно
открыты IDE/браузер/другие тяжёлые программы. Признаки: `mvn test` внезапно
обрывается без "BUILD FAILURE"/"BUILD SUCCESS" в конце, эмулятор/Appium ещё живы. Это
не баг тестов — см. раздел 3.3 про батчи.

### 3.3. Прогон батчами (если полный прогон не помещается в память)

Раздели `testng.xml` на несколько маленьких сьютов по 2-3 класса и гоняй их по
очереди, с очисткой состояния приложения между батчами. Пример на 5 батчей:

```bash
# Сгенерировать батч-файлы (разово, или храни их в репозитории, если часто нужны)
python3 - <<'EOF'
import re
with open('src/test/resources/testng.xml') as f:
    content = f.read()
listeners = re.search(r'<listeners>.*?</listeners>', content, re.S).group(0)
test_blocks = re.findall(r'<test name="[^"]*">.*?</test>', content, re.S)
batches = [test_blocks[i:i+3] for i in range(0, len(test_blocks), 3)]
for idx, batch in enumerate(batches, start=1):
    suite = f'''<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">
<suite name="TezChakana Batch {idx}" verbose="1">
    {listeners}
{chr(10).join(batch)}
</suite>
'''
    with open(f"/tmp/batch{idx}.xml", "w") as f:
        f.write(suite)
EOF

# Прогнать батч, почистить состояние приложения перед следующим
for i in 1 2 3 4 5; do
    adb shell am force-stop uz.agrobank.chakanaexpress
    adb shell am start -n uz.agrobank.chakanaexpress/.MainActivity
    sleep 4
    mvn test -DsuiteXmlFile=/tmp/batch$i.xml
    # если память проседает между батчами - перезапусти эмулятор (см. раздел 1)
done
```

Если эмулятор явно "тупит" между батчами (долгие паузы, всё замедляется) — перезапусти
его (раздел 1) перед следующим батчем, это дешевле, чем ловить ложные падения.

### 3.4. Один класс или один метод

```bash
# Весь класс
mvn test -Dtest=SettingsTest

# Один метод
mvn test -Dtest=SettingsTest#faqOpensInApp

# Несколько методов
mvn test -Dtest=SettingsTest#faqOpensInApp+privacyPolicyOpensInApp
```

⚠️ **Важная особенность**: `-Dtest=...` использует другой путь выполнения Maven
Surefire (`TestNGDirectoryTestSuite`), который **не подключает `<listeners>` сьюта**
— это значит, автоматический скриншот при падении (`ScreenshotOnFailureListener`) и
автоповтор (`RetryAnalyzerTransformer`) **не сработают**. Для точечной проверки одного
метода это нормально, но не делай выводов про ретраи/скриншоты по такому прогону —
для этого нужен полный сьют через `-DsuiteXmlFile=...`.

## 4. Диагностика упавшего теста

1. **Скриншот в момент падения** — `target/screenshots/<Класс>.<метод>-<таймстамп>.png`.
   Смотри его в первую очередь, прежде чем перезапускать что-либо вручную — обычно
   сразу видно, на каком экране всё пошло не так.
2. **Полный лог** — `target/logs/tests.log` (Logback, см. `logback.xml`). Там
   preflight-чеклист (эмулятор/Appium доступны), ретраи, сохранённые скриншоты — больше
   деталей, чем в консоли Maven.
3. **Автоповтор** — каждый упавший тест повторяется один раз автоматически
   (`RetryOnce`/`RetryAnalyzerTransformer`, подключены через `<listeners>` в обоих
   сьютах). Второе падение подряд считается настоящим провалом, не флаком.
4. Если упало **много не связанных друг с другом тестов подряд** — почти наверняка
   один из более ранних тестов оставил приложение в незнакомом состоянии (застрял
   диалог, не закрылась корзина, экран логина и т.п.), и `returnToHomeScreen()` не
   смог с него восстановиться. Смотри скриншот САМОГО ПЕРВОГО упавшего теста в
   прогоне — обычно там ответ, а не в тесте, который упал третьим по счёту. Это ровно
   та ошибка, из-за которой в проекте появились SYS-13/SYS-16/SYS-17 (все в
   exploration-notes.md) — читай их, если ловишь что-то похожее.

## 6. Как устроен POM в этом проекте (обязательно прочитай перед тем, как писать код)

### Базовая идея

- **`screens/*.java`** — по одному классу на экран приложения. Внутри — приватные
  локаторы (`By`) и публичные методы вида `verifyXxx()` (проверка, возвращает `this`
  или другой экран) / `openXxx()` (навигация, возвращает объект следующего экрана).
  **Никаких `Assert`/локаторов прямо в `@Test`-методах** — вся логика взаимодействия с
  UI живёт в `screens/`, тест только вызывает цепочку методов.
- **`tests/*.java`** — тонкий слой: один `@Test`-метод = одна цепочка вызовов на
  экранах. Смотри `SettingsTest.java` как эталонный маленький пример:

```java
@Test(groups = "safe")
public void faqOpensInApp() {
    new HomeScreen(driver)
            .openProfileTab()
            .openSettings()
            .verifyFaqOpensInApp();
}
```

- **`BaseTest.java`** — `@BeforeMethod`/`@AfterMethod` поднимают/гасят Appium-сессию
  для КАЖДОГО `@Test`-метода отдельно (не для класса целиком). Именно поэтому
  состояние приложения (`NoReset(true)`) "переезжает" из теста в тест — сессия новая,
  а данные приложения старые.
- **`BaseScreen.java`** — общие помощники, которые нужны почти каждому экрану:
  `waitFor(locator)` (ожидание с обработкой случайных системных/стартовых диалогов,
  см. код), `tapAt(x, y)` + `scaledX()/scaledY()` (координатный тап с масштабированием
  под реальный размер экрана устройства), `swipeUpOnScreen()/swipeDownOnScreen()`,
  `typeViaAdb()` (см. раздел 8 про ввод текста).

### Группы риска (`groups` в `@Test`)

Каждый `@Test` обязан быть помечен одной из трёх групп:

| Группа | Значение |
|---|---|
| `safe` | Read-only, не меняет реальный аккаунт |
| `mutating` | Меняет реальные данные (корзина/адрес/язык/уведомления), но обратимо и без денег |
| `destructive` | Может создать реальный заказ — такие тесты не подключаются в сьюты без отдельного разговора с владельцем |

### Почему так много координатных тапов вместо `.click()`

Это Flutter-приложение, и у него специфика: многие интерактивные элементы (нижняя
CTA-кнопка, вкладки нижней навигации, кнопки в шторках) **смержены Flutter'ом в один
accessibility-узел на весь экран/большую область** — у них нет своего отдельного
кликабельного под-элемента. `.click()` в таком случае попадает по центру экрана, а не
по самой кнопке. Обходной путь, использованный везде в проекте: снять координаты
кнопки на эталонном скриншоте (обычно 1080x2400) и тапать по ним через
`tapAt(scaledX(refX), scaledY(refY))` — `scaledX/scaledY` пересчитывают координату под
реальный размер экрана устройства, на котором сейчас идёт тест.

**Когда добавляешь новый экран с такой кнопкой**: сначала попробуй найти нормальный
locator (`accessibility id`/`content-desc`, `resource-id`) через дамп дерева
доступности (`adb shell uiautomator dump` или Appium Inspector — см. раздел 8). Только
если элемент реально смержен (в дампе видно, что у нужной тебе кнопки нет
своего/отдельного узла) — переходи на координатный тап, и обязательно оставь
комментарий, почему (см. любой пример в `BaseScreen.java`/`SettingsScreen.java` —
стиль комментариев в этом проекте: что произошло, что попробовали, что сработало).

## 7. Как написать новый тест — пошагово

Пример: допустим, нужно покрыть новый экран "Избранное" (Sevimlilar).

### Шаг 1. Разведка экрана вручную

Прежде чем писать код, посмотри на реальный экран и его дерево доступности:

```bash
# Открой экран вручную на эмуляторе, затем сними дамп дерева:
adb shell uiautomator dump /sdcard/window_dump.xml
adb pull /sdcard/window_dump.xml .
cat window_dump.xml | grep -o 'content-desc="[^"]*"'   # быстрый список всех content-desc на экране
```

Ищи `content-desc` (это то, что матчится через `AppiumBy.accessibilityId(...)`) у
нужных тебе элементов. Если у элемента нет `content-desc` и `resource-id` — это,
вероятно, тот самый смерженный узел (см. раздел 6), придётся снимать `bounds` и делать
координатный тап.

Альтернатива — Appium Inspector (GUI-приложение) с той же Appium-сессией, что описана
в разделе 1: удобнее кликать по элементам мышкой и сразу видеть их атрибуты.

### Шаг 2. Создать `screens/FavoritesScreen.java`

```java
package com.tezchakana.screens;

import io.appium.java_client.AppiumBy;
import io.appium.java_client.android.AndroidDriver;
import org.openqa.selenium.By;
import org.testng.Assert;

public class FavoritesScreen extends BaseScreen {

    private static final By SCREEN_TITLE = AppiumBy.accessibilityId("Sevimlilar");
    // ... остальные локаторы, снятые на шаге 1

    public FavoritesScreen(AndroidDriver driver) {
        super(driver);
    }

    public FavoritesScreen verifyScreenShown() {
        Assert.assertTrue(waitFor(SCREEN_TITLE).isDisplayed(), "Экран \"Sevimlilar\" не открылся");
        return this;
    }
}
```

Держись стиля, который уже используется во всём проекте:
- Локаторы — `private static final By` вверху класса, с комментарием, откуда взяты
  (особенно если координатный тап — обязательно объясни, почему не locator).
- Методы `verifyXxx()` возвращают `this` (для цепочки дальше на том же экране) либо
  новый экран, если метод переводит на другой экран.
- Сообщения в `Assert` — на русском, конкретные ("не отображается", "не открылся"), не
  просто "assertion failed".

### Шаг 3. Добавить точку входа на новый экран из существующего

Если "Sevimlilar" открывается, например, иконкой сердца на `HomeScreen` — добавь метод
туда:

```java
// в HomeScreen.java
public FavoritesScreen openFavorites() {
    returnToHomeScreen();
    tapAt(scaledX(FAVORITES_ICON_REF_X), scaledY(FAVORITES_ICON_REF_Y)); // или .click() если есть locator
    return new FavoritesScreen(driver);
}
```

### Шаг 4. Создать `tests/FavoritesTest.java`

```java
package com.tezchakana.tests;

import com.tezchakana.screens.HomeScreen;
import org.testng.annotations.Test;

/**
 * Sevimlilar (избранное): FAV-01 (см. docs/exploration-notes.md).
 */
public class FavoritesTest extends BaseTest {

    @Test(groups = "safe")
    public void favoritesScreenShown() {
        new HomeScreen(driver)
                .openFavorites()
                .verifyScreenShown();
    }
}
```

### Шаг 5. Подключить в сьюты

Добавь `<test>`-блок в `testng.xml` (и в `testng-safe.xml`, если метод помечен
`safe`) — по образцу уже существующих блоков:

```xml
<test name="Favorites">
    <classes>
        <class name="com.tezchakana.tests.FavoritesTest"/>
    </classes>
</test>
```

### Шаг 6. Проверить живьём ПЕРЕД коммитом

```bash
mvn test -Dtest=FavoritesTest
```

Прогони минимум дважды подряд (флаки часто не видны с первого раза — особенно если
экран открывается с анимацией/подгрузкой сети). Только после этого добавляй в
`docs/exploration-notes.md` строку в таблицу покрытия (найди похожий раздел, добавь
свой ID кейса типа `FAV-01`, статус `✅`, ссылку на тест).

### Шаг 7. Не забыть про уборку за собой

Если тест что-то меняет (кладёт товар в корзину, открывает диалог, меняет настройку) —
верни состояние обратно ДО конца теста, а не полагайся, что следующий тест сам
разберётся. Смотри `CheckoutFlowTest.java` — там `try/finally` с явной очисткой
корзины, потому что это уже дважды ломало весь остаток прогона (SYS-13, коммит с
похожим сообщением). Если сомневаешься — открой `docs/exploration-notes.md` и
поищи "SYS-13"/"SYS-16", это готовый пример того, как выглядит такой баг на практике.

## 8. Как поменять существующий тест или локатор

### Приложение изменилось, локатор перестал находиться

1. Сними свежий дамп дерева доступности того же экрана (раздел 7, шаг 1) и сравни с
   тем, что в коде — обычно меняется либо текст (`content-desc`), либо структура
   (элемент теперь смержен по-другому).
2. Поменяй `By`-константу в соответствующем `screens/*.java`. **Не трогай** файл в
   `tests/` — он не должен знать про локаторы вообще.
3. Прогони живьём (`mvn test -Dtest=<Класс>`) минимум дважды, прежде чем коммитить.
4. Если старое поведение экрана было задокументировано в `docs/exploration-notes.md`
   как известный баг/особенность — обнови соответствующую строку, не оставляй
   устаревшее описание.

### Тест стал нестабильным (иногда падает без изменений в коде)

- Сначала исключи истощение памяти эмулятора (раздел 1) — самая частая причина
  "необъяснимой" нестабильности в этом проекте.
- Проверь скриншот падения — если тест падает на экране, который он вообще не должен
  видеть, скорее всего проблема не в НЁМ, а в предыдущем тесте, оставившем "грязное"
  состояние (см. раздел 4, последний пункт).
- Не добавляй `Thread.sleep()` "на всякий случай" — если нужна пауза, используй
  `waitFor(locator)` на что-то конкретное, что появляется после нужного события
  (см. `BaseScreen.waitFor()`), это надёжнее и не тормозит прогон, когда пауза не
  нужна.

### Ввод текста в поле не срабатывает

В этом Flutter-приложении обычный Appium/Selenium `sendKeys()`/`setValue()`
**ненадёжен** на кастомных текстовых полях (проверено многократно вживую). Рабочий
способ — `typeViaAdb(text)` из `BaseScreen` (эмулирует реальные IME-события через
`adb shell input text`), уже используется в `OtpScreen.enterCode()` — бери оттуда
пример.

## 9. Git-конвенции этого проекта

- Коммить только то, что реально проверено живьём (см. историю коммитов — почти в
  каждом сообщении есть "проверено вживую"/"verified live"). Не коммить код, который
  "должен сработать" без реальной проверки на эмуляторе.
- Сообщения коммитов объясняют **почему**, не только что — если фиксишь баг, опиши
  условие, при котором он воспроизводился, и как проверил, что фикс реально работает.
- `config.properties` никогда не коммитится (реальные номер/OTP) — если случайно
  добавил, `git reset HEAD src/test/resources/config.properties` и провентилируй
  `.gitignore`.
- Не проси и не жди согласия на пуш "по умолчанию" — но подтверждай перед `git push`,
  если работаешь в паре с кем-то ещё, кто может пушить параллельно.

  официальной документации Flutter.
